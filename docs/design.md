# Nakabisha Trainer 設計書

## 1. プロジェクトの目的

Nakabisha Trainer は、自分の中飛車の棋譜を蓄積・分析し、相手の駒配置や局面ごとの評価値から、自分が苦手としている局面や相手の構えを発見するための将棋支援ツールである。

将棋エンジンそのものの強さを競うのではなく、既存の将棋エンジンを活用して中飛車の研究を支援することを目的とする。

最終的には、自分の棋譜から苦手局面を発見し、その局面を練習問題として利用できるようにする。

## 2. 基本方針

- 戦型名を完全に判定することよりも、局面から取得できる特徴量を扱うことを優先する。
- 中飛車判定は、序盤の数手を見たうえで飛車が5筋へ振られていることなど、比較的単純な条件から開始する。
- 相手の戦型を完全に分類することは目標とせず、玉・銀・飛車・角・歩などの一部の駒配置を特徴量として抽出する。
- 元棋譜を基本データとして保存し、棋譜から再計算可能な情報は必要に応じて再生成する。
- 全局面の解析結果を無条件に保存するのではなく、評価値が大きく変化した重要局面など、研究に必要な情報を選択して保存する。
- 性能上の問題が実際に発生するまでは、分かりやすさと保守性を優先する。
- ただし、盤面表現などの内部実装を将来的に Bitboard 等へ置き換えられるよう、上位層から実装詳細を隠蔽する。

## 3. Ver.0.1 の目標

Ver.0.1 では、将棋の基本モデルを構築する。

目標は、正しい棋譜が与えられたとき、指し手を順番に適用して各局面を正確に再構築できることである。

Ver.0.1 では将棋の完全なルール実装を目的としない。王手・詰み・千日手・二歩・打ち歩詰めなどの判定は、必要になったバージョンで追加する。

## 4. 基本モデル

### 4.1 `Side`

先手・後手を表す。

```text
SENTE
GOTE
```

### 4.2 `PieceType`

駒の種類を表す。

コード上ではチェス由来の `PAWN` や `ROOK` 等ではなく、将棋の日本語名称をローマ字表記した名前を使用する。

```text
FU
KYOSHA
KEIMA
GIN
KIN
KAKU
HISHA
OU
```

成りは駒種そのものには含めず、`Piece` の `promoted` で表現する。

### 4.3 `Piece`

盤上に存在する具体的な駒を表す。

```text
Piece
├── Side side
├── PieceType type
└── boolean promoted
```

例えば、先手の成っていない飛車は `SENTE + HISHA + false`、先手の成銀は `SENTE + GIN + true` とする。

### 4.4 `Square`

9×9 の盤上の位置を表す。

内部的には筋・段を整数等で表現し、将棋の座標を安全に扱える型として提供する。

### 4.5 `Move`

1手の指し手を表す。

通常の移動と駒打ちを区別できる構造にする。

概念上は以下を保持する。

```text
Move
├── MoveType type
├── Square from
├── Square to
├── PieceType pieceType
└── boolean promotion
```

駒打ちでは `from` を使用しない。

### 4.6 `Position`

ある時点の局面を表す。主な状態は以下のとおり。

```text
Position
├── 盤上の駒
├── 先手の持ち駒
├── 後手の持ち駒
└── 手番
```

外部からは盤面の取得や指し手の適用を行えるAPIを提供し、内部の盤面表現には依存しない設計とする。

初期局面を生成する `Position.initial()` を用意する。

### 4.7 `GameRecord`

1局の棋譜を表す。

```text
GameRecord
├── 対局情報
├── 結果
└── List<Move> moves
```

棋譜から局面を順番に再構築できるようにする。

## 5. Position の変更方針

基本モデルとして扱いやすい `Position` を提供しつつ、大量の棋譜を処理する場合に備えて、将来的には `MutablePosition` のような再生・解析用の内部モデルを導入できる構造を想定する。

必要に応じて、

```text
apply(move)
undo(move)
```

のような操作で盤面を使い回せるようにする。

これにより、すべての手で新しい盤面を完全に複製する実装を避けられるようにする。

## 6. 盤面表現と性能

Ver.0.1 では、理解しやすい単純な盤面表現を優先する。

ただし、`Position` の利用者が内部実装に依存しないようにし、必要になった場合に以下のような実装へ変更できるようにする。

```text
単純な配列等
    ↓
Bitboard
```

将棋盤は81マスあるため、オセロのように単一の64bit値だけで盤面を表すことはできないが、複数の整数を組み合わせた Bitboard 表現は可能である。

将来的に自前の探索エンジンを作る場合や大量の局面を高速処理する必要が生じた場合に検討する。

## 7. 局面特徴の分離

局面そのものを表す `Position` に、中飛車判定や戦型判定のロジックを直接持たせない。

将来的に以下のような分離を行う。

```text
Position
    ↓
PositionFeatureExtractor
    ↓
PositionFeatures
```

これにより、戦型判定や特徴量の定義を変更しても、基本的な局面モデルを変更せずに済むようにする。

## 8. 中飛車判定

中飛車判定は、最初から完全な戦型認識を目指さない。

例えば先手の場合、序盤に飛車が5筋へ移動していること、5筋の歩の状態など、複数の単純な条件を組み合わせて中飛車候補・中飛車と判定する。

相手側については、戦型名を完全に分類するのではなく、玉や銀など一部の駒配置を特徴として抽出する。

## 9. 将棋エンジン連携

将棋エンジンそのものは実装せず、将来的に USI を利用して既存エンジンと連携する。

```text
Nakabisha Trainer
        ↓
      USI
        ↓
既存将棋エンジン
```

取得した評価値や候補手を、棋譜の局面分析に利用する。

## 10. 重要局面と苦手分析

全局面のエンジン解析結果を無条件に保存するのではなく、評価値が大きく変化した局面などを重要局面として抽出する。

将来的には、例えば以下のような特徴と評価値変化を集計する。

```text
中飛車
+ 相手居飛車
+ 相手銀6四
+ 相手玉8八
        ↓
評価値が大きく落ちやすい
```

この集計結果から、自分が苦手とする局面や相手の構えを発見する。

## 11. データ保存

基本データとして棋譜を保存する。

局面から再計算可能な情報は、原則として元棋譜から再生成できるようにする。

将来的には SQLite を利用して棋譜・重要局面・解析結果等を保存する。

また、同一局面の再解析を避けるため、将来的に Zobrist Hash を利用した解析キャッシュを導入する。

```text
Position
    ↓
Zobrist Hash
    ↓
Analysis Cache
```
