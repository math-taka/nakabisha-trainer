# Nakabisha Trainer 設計書

## 1. プロジェクトの目的

Nakabisha Trainer は、自分の中飛車の棋譜を蓄積・分析し、相手の駒配置や局面ごとの評価値から、自分が苦手としている局面や相手の構えを発見するための将棋支援ツールである。

将棋エンジンそのものの強さを競うのではなく、既存の将棋エンジンを活用して中飛車の研究を支援することを目的とする。

最終的には、自分の棋譜から苦手局面を発見し、その局面を練習問題として利用できるようにする。

## 2. 基本方針

- 戦型名を完全に判定することよりも、局面から取得できる特徴量を扱うことを優先する。
- 中飛車判定は、序盤の数手を見たうえで飛車が5筋へ振られていることなど、比較的単純な条件から開始する。
- 相手の戦型を完全に分類することは目標とせず、玉・銀・飛車・角・歩などの一部の駒配置を特徴量として抽出する。
- 元棋譜を基本データとして保存し、棋譜から再計算可能な情報は必要に応じて再生成する。
- 全局面の解析結果を無条件に保存するのではなく、評価値が大きく変化した重要局面など、研究に必要な情報を選択して保存する。
- 性能上の問題が実際に発生するまでは、分かりやすさと保守性を優先する。
- ただし、盤面表現などの内部実装を将来的に Bitboard 等へ置き換えられるよう、上位層から実装詳細を隠蔽する。

## 3. Ver.0.1 の実装内容

将棋の棋譜と局面を扱うための基本モデルを実装した。

以下のクラスを作成した。

- `Side`：先手・後手を表す
- `PieceType`：駒種を表す
- `Piece`：駒の所属、駒種、成り状態を表す
- `Square`：盤上の座標を表す
- `Move`：1手の指し手を表す
- `Position`：盤面、持ち駒、手番などの1局面を表す
- `GameRecord`：1局分の指し手列を保持する

`Move`には通常の駒移動だけでなく、駒取り、成り、駒打ちを表現できるようにした。

`GameRecord`に記録された指し手を順番に`Position`へ適用することで、棋譜の任意の手数まで局面を再構築できるようにした。

`GameRecord.positionAt(int ply)` は指定した手数まで指し手を適用した局面を返し、`GameRecord.currentPosition()` は全指し手を適用した現在局面を返す。

また、実際のKIF棋譜4局の序盤20手を用いたJUnitテストを作成し、指し手の適用と局面再構築が正しく行われることを確認した。

Ver.0.1ではKIFファイルそのものの読み込みは行わず、指し手は`Move`として直接与える。KIFファイルの読み込みはVer.0.2で実装する。

## 4. Ver.0.2 KIF棋譜読み込み・GameRecord生成・局面再生

### 4.1 目的

KIF形式の棋譜ファイルを読み込み、`GameRecord`を生成できるようにする。

KIFファイルの読み込み、1行の指し手の変換、`GameRecord`の生成をそれぞれ分離し、以下の責務を持たせる。

- `KifReader`：KIFファイルから指し手行を抽出する
- `KifMoveConverter`：1行のKIF指し手を`Move`へ変換する
- `KifGameRecordReader`：上記2つを組み合わせて`GameRecord`を生成する

### 4.2 基本構成

```text
KIFファイル
    ↓
KifReader.read(Path)
    ↓
List<String>
    ↓
KifGameRecordReader
    ├── KifMoveConverter
    ↓
GameRecord
    ↓
Position.apply(Move)
    ↓
Position
```

`KifReader`と`KifMoveConverter`は直接依存させず、それぞれの責務を分離する。

`KifGameRecordReader`では、`KifReader`が抽出した指し手行を`KifMoveConverter`で`Move`へ変換し、`GameRecord`へ順番に追加する。

KIFの「同」は、`KifMoveConverter`では`to = null`として表現する。その後、`KifGameRecordReader`が直前の指し手の移動先を使って実際の移動先を解決する。

### 4.3 KifReader

`KifReader`はKIFファイルの読み込みを担当する。

以下の静的メソッドを公開APIとし、KIFファイルから指し手行を抽出して返す。

```java
public static List<String> read(Path path)
```

指し手行の文字列は加工せず、消費時間などの付加情報を含めてKIFファイルに記述された状態のまま返す。

KIFの指し手の意味の解析や`Move`への変換は`KifMoveConverter`の責務とする。

### 4.4 KIFの読み込み範囲

現時点では、`Move`の生成に必要となる指し手関連の情報のみを扱う。

対象には以下を含む。

- 指し手番号
- 通常の指し手
- `同`
- 移動元
- 成り
- 駒打ち

一方、以下の情報は現時点では利用せず読み飛ばす。

- 対局者・日時・棋戦などのヘッダ情報
- コメント
- 空行・見出し
- 消費時間
- 勝敗・投了などの終局情報

### 4.5 文字コード

`.kif`ファイルはWindows-31Jとして読み込む。

`.kifu`形式（UTF-8）は現時点では対象外とする。

### 4.6 エラー処理

現時点の実装では、KIFの変換に失敗した場合は`IllegalArgumentException`を使用する。

```text
ファイルの読み込み失敗
    → IOException

対応していないKIF指し手や変換できない入力
    → IllegalArgumentException
```

`KifParseException`や`UnsupportedKifException`などの専用例外は、現時点では導入しない。

### 4.7 指し手行の加工

`KifReader`では指し手行を解釈・加工しない。

消費時間などの付加情報も含め、KIFに記述されている文字列をそのまま`List<String>`に格納する。KIF文字列の解析や不要な情報の除去は`KifMoveConverter`側で行う。

### 4.8 指し手以外の行

ヘッダ、空行、コメント、見出し、終局情報などは現時点では読み飛ばす。

`KifReader`では指し手行を識別し、それ以外の行は`GameRecord`生成の対象にしない。

### 4.9 KifMoveConverter

`KifMoveConverter`は、1行のKIF指し手文字列を解釈して`Move`を1つ生成する責務を持つ。

公開メソッドは以下とする。

```java
public static Move convert(String line)
```

KIFの各要素は既存の`Move`仕様に対応させる。

| KIFの要素 | `Move`への対応 |
|---|---|
| 指し手番号 | `side`の判定に利用し、`Move`には番号自体を保持しない |
| 移動先 | `to` |
| 駒 | `pieceType` |
| 移動元 | `from` |
| 成り | `promotion = true` |
| `同` | `to = null` |
| `打` | `from = null` |
| 消費時間 | 無視 |

指し手番号は奇数を`Side.SENTE`、偶数を`Side.GOTE`として扱う。

`Square(file, rank)`の座標は棋譜表記と対応させる。例えば「５三」は`Square(5, 3)`とする。

### 4.10 KIF特有の表現

`右`、`左`、`直`、`引`、`寄`、`上`などの修飾は、現在のKIF形式では移動元が`(筋)(段)`として明示されるため、`Move`には保持しない。

成駒は`PieceType`に独立した成駒の種類を追加せず、`promoted`で表現する。現在対応している成駒表記は以下のとおり。

| KIF表記 | `PieceType` | `promoted` |
|---|---|---|
| `と` | `FU` | `true` |
| `成香` | `KYO` | `true` |
| `成桂` | `KEI` | `true` |
| `成銀` | `GIN` | `true` |
| `馬` | `KAKU` | `true` |
| `龍` | `HI` | `true` |
| `竜` | `HI` | `true` |

投了、時間切れなどの終局情報は`Move`への変換対象としない。

### 4.11 KifGameRecordReader

`KifGameRecordReader`は、KIFファイルから`GameRecord`を生成する責務を持つ。

公開メソッドは以下とする。

```java
public static GameRecord read(Path path) throws IOException
```

処理の流れは以下のとおり。

```text
KIFファイル
    ↓
KifReader.read(Path)
    ↓
指し手行
    ↓
KifMoveConverter.convert(String)
    ↓
Move
    ↓
「同」の移動先を直前のMoveのtoから解決
    ↓
GameRecord.addMove(Move)
```

`KifMoveConverter`は1行のKIF表現を`Move`へ変換することに専念し、複数の指し手の関係を必要とする`同`の解決は`KifGameRecordReader`が担当する。

### 4.12 `Move`におけるKIFの「同」の扱い

KIFの「同」は、`KifMoveConverter`の段階では移動先を確定させず、`to = null`として表現する。

`KifGameRecordReader`では直前の指し手の移動先を`previousTo`として保持し、「同」の指し手を処理するときにその値を実際の`to`として設定する。

これにより、KIF文字列の解析と複数手にまたがる文脈依存の処理を分離する。

### 4.13 テスト方針

`KifReader`については、指し手行だけが抽出され、読み飛ばすべき行が含まれず、必要な行が欠落せず、順序と文字列が維持されることをテストする。

`KifMoveConverter`については、正常なKIF指し手が正しい`Move`へ変換されることをテストする。通常の指し手、成り、駒打ち、「同」、成駒表記などを対象とする。

`KifGameRecordReader`については、実際のKIFファイルから`GameRecord`を生成できること、および「同」の移動先が正しく解決されることをテストする。

さらに、実際のKIF棋譜4局を読み込み、序盤20手を`Position`へ適用して局面を再構築する統合テストを行う。

使用するKIFファイルは以下の4局とする。

- `sente_nakabisha.kif`
- `gote_nakabisha1.kif`
- `sente_ibisha.kif`
- `gote_mukaibisha.kif`

統合テストでは、実際に確認済みの盤上の駒配置、持ち駒、手番のみを期待値として使用する。

### 4.14 完了条件

以下を満たした時点でVer.0.2を完了とする。

- KIFファイルから指し手行を読み込める
- KIFの指し手を`Move`へ変換できる
- KIFの「同」を解決できる
- KIFから`GameRecord`を生成できる
- `GameRecord`から`Position`を再生できる
- 実際のKIF棋譜4局の序盤20手について統合テストが通る

Ver.0.2では、実際のKIFファイルから`GameRecord`を生成し、そこから`Position`を再生する一連の流れを実装・確認済みとする。

## 6. 基本モデル

### 6.1 `Side`

先手・後手を表す。

```text
SENTE
GOTE
```

### 6.2 `PieceType`

駒の種類を表す。

コード上ではチェス由来の `PAWN` や `ROOK` 等ではなく、将棋の日本語名称をローマ字表記した名前を使用する。

```text
FU
KYO
KEI
GIN
KIN
KAKU
HI
OU
```

王と玉は同じ `OU` として扱う。

成りは駒種そのものには含めず、`Piece` の `promoted` で表現する。

### 6.3 `Piece`

盤上に存在する具体的な駒を表す。

```text
Piece
├── Side side
├── PieceType type
└── boolean promoted
```

例えば、先手の成っていない飛車は `SENTE + HI + false`、先手の成銀は `SENTE + GIN + true` とする。

### 6.4 `Square`

9×9 の盤上の位置を表す。

`Square(file, rank)` の `file` は棋譜で使用する「筋」（1〜9）、`rank` は「段」（1〜9）を表す。したがって、例えば `Square(2, 8)` は棋譜上の「２八」、`Square(8, 2)` は「８二」に対応する。

この座標系では、初期配置の飛車と角は以下の位置になる。

```text
後手飛車: (8, 2)
後手角  : (2, 2)
先手角  : (8, 8)
先手飛車: (2, 8)
```

`Square` は筋・段を1〜9の範囲に制限し、盤面配列の内部インデックスへの変換も提供する。

### 6.5 `Move`

1手の指し手を表す。

実装では以下の6つの情報を保持する。

```text
Move
├── Side side
├── Square from
├── Square to
├── PieceType pieceType
├── boolean promoted
└── boolean promotion
```

`promoted`は、その指し手で動かす駒が指し手開始時点ですでに成っているかどうかを表す。

`promotion`は、その指し手によって駒が成るかどうかを表す。

通常の駒の移動では`from`と`to`の両方を持つ。駒打ちでは`from = null`とする。また、KIFの「同」を変換した直後の状態では`to = null`とする。

`isDrop()`で駒打ちかどうかを判定でき、`isSameDestination()`でKIFの「同」に対応する未解決の移動先かどうかを判定できる。

`Move`のコンストラクタでは、駒打ちに対する成り（`from == null && promotion == true`）を不正として扱う。

### 6.6 `Position`

ある時点の局面を表す。主な状態は以下のとおり。

```text
Position
├── 盤上の駒
├── 先手の持ち駒
├── 後手の持ち駒
└── 手番
```

外部からは盤面の取得や指し手の適用を行えるAPIを提供し、内部の盤面表現には依存しない設計とする。

初期局面を生成する `Position.initial()` を用意する。初期局面では盤上の駒を将棋の標準初期配置に設定し、先手・後手の持ち駒を空、手番を先手とする。

`Position.apply(Move)`では、指し手を適用した新しい`Position`を生成する。駒取りが発生した場合、取った側の持ち駒へ駒を追加し、成駒を取った場合は成る前の駒種として持ち駒へ追加する。

`Position`自身は棋譜の履歴を保持しない。

### 6.7 `GameRecord`

`GameRecord`は1局分の指し手列を表す。

以下の情報を保持する。

- `List<Move> moves`

局面そのものを履歴として保持するのではなく、指し手列を基本データとする。必要な局面は初期局面から指し手を順番に適用することで再構築する。

`positionAt(int ply)`により、指定した手数まで指し手を適用した局面を取得できる。

`currentPosition()`により、全指し手を適用した現在局面を取得できる。

## 7. Position の変更方針

基本モデルとして扱いやすい`Position`を提供しつつ、大量の棋譜を処理する場合に備えて、将来的には`MutablePosition`のような再生・解析用の内部モデルを導入できる構造を想定する。

必要に応じて、

```text
apply(move)
undo(move)
```

のような操作で盤面を使い回せるようにする。

これにより、すべての手で新しい盤面を完全に複製する実装を避けられるようにする。

## 8. 盤面表現と性能

Ver.0.1では、理解しやすい単純な盤面表現を優先する。

ただし、`Position`の利用者が内部実装に依存しないようにし、必要になった場合に以下のような実装へ変更できるようにする。

```text
単純な配列等
    ↓
Bitboard
```

将棋盤は81マスあるため、オセロのように単一の64bit値だけで盤面を表すことはできないが、複数の整数を組み合わせたBitboard表現は可能である。

将来的に自前の探索エンジンを作る場合や大量の局面を高速処理する必要が生じた場合に検討する。

## 9. 局面特徴の分離

局面そのものを表す`Position`に、中飛車判定や戦型判定のロジックを直接持たせない。

以下のように分離する。

```text
Position
    ↓
PositionFeatureExtractor
    ↓
PositionFeatures
```

これにより、戦型判定や特徴量の定義を変更しても、基本的な局面モデルを変更せずに済むようにする。

## 10. 中飛車判定

中飛車判定は、最初から完全な戦型認識を目指さない。

例えば先手の場合、序盤に飛車が5筋へ移動していること、5筋の歩の状態など、複数の単純な条件を組み合わせて中飛車候補・中飛車と判定する。

相手側については、戦型名を完全に分類するのではなく、玉や銀など一部の駒配置を特徴として抽出する。

Ver.0.3では、まず飛車・角・玉・銀などの位置を特徴量として取得し、その特徴量を利用した中飛車判定を実装する。

## 11. 将棋エンジン連携

将棋エンジンそのものは実装せず、将来的にUSIを利用して既存エンジンと連携する。

```text
Nakabisha Trainer
        ↓
      USI
        ↓
既存将棋エンジン
```

取得した評価値や候補手を、棋譜の局面分析に利用する。

## 12. 重要局面と苦手分析

全局面のエンジン解析結果を無条件に保存するのではなく、評価値が大きく変化した局面などを重要局面として抽出する。

将来的には、例えば以下のような特徴と評価値変化を集計する。

```text
中飛車
+ 相手居飛車
+ 相手銀6四
+ 相手玉8八
        ↓
評価値が大きく落ちやすい
```

この集計結果から、自分が苦手とする局面や相手の構えを発見する。

## 13. データ保存

基本データとして棋譜を保存する。

局面から再計算可能な情報は、原則として元棋譜から再生成できるようにする。

将来的にはSQLiteを利用して棋譜・重要局面・解析結果等を保存する。

また、同一局面の再解析を避けるため、将来的にZobrist Hashを利用した解析キャッシュを導入する。

```text
Position
    ↓
Zobrist Hash
    ↓
Analysis Cache
```
